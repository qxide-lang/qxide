# `qxide build`: 번들 실행 파일 (Stage 3a)

## 상태

`feat/general-purpose` 브랜치에 구현되었다(로컬 구현이며 아직 릴리스되지 않았다). 범용 언어 로드맵(`docs/design/general-purpose-roadmap.md`)의 Stage 3a에 해당한다.

이 기능은 네이티브 컴파일이 아니다. 생성된 실행 파일에는 `qxide` 인터프리터(`ast`, `ir` 엔진, 그리고 빌드에 사용한 `qxide` 바이너리가 `jit` Cargo 피처로 빌드된 경우에만 `jit` 엔진)가 그대로 포함되며, 프로그램을 `qxide run`과 동일한 방식으로 실행한다.

## 사용법

```text
qxide build [FILE] [-o OUT] [--engine ast|ir|jit] [--shots N] [--seed S] [--allow fs]
```

- `FILE`을 생략하면 `qxide run`과 마찬가지로 현재 디렉터리 주변 프로젝트의 `src/main.qx`를 빌드한다.
- `-o`를 생략하면 현재 디렉터리에 입력 파일 이름에서 확장자를 제외한 이름으로 출력 파일을 만든다. 프로젝트의 `src/main.qx`를 빌드할 때는 패키지 이름을 출력 이름으로 사용한다(예: 패키지 `demo`이면 `demo`).
- Windows에서는 출력 이름에 확장자가 없으면 `.exe`를 자동으로 붙인다.

```text
$ qxide build examples/cli/wc.qx --allow fs -o wc.exe
$ wc.exe -f < notes.txt
```

## 동작

### 빌드

1. CLI 권한(`--allow fs` 지정 시 `std.fs` 추가)으로 `qxide check`와 동일하게 프로그램을 검사한다. 오류가 하나라도 있으면 진단을 출력하고 종료 코드 `1`로 종료하며 출력 파일은 생성하지 않는다.
2. 검사하는 동안 링커가 읽은 모든 모듈 파일(프로그램 자체 모듈과 패키지 의존성의 모듈)을 읽은 경로와 함께 기록한다. 프로젝트의 패키지 테이블(패키지 이름, 소스 디렉터리, 각 패키지가 임포트할 수 있는 의존성 목록)도 함께 기록한다.
3. 출력 파일은 `실행 중인 qxide 실행 파일의 사본 + 페이로드 + 32바이트 트레일러` 순서로 구성한다. 출력 경로 옆의 임시 파일에 먼저 기록한 뒤 대상 위치로 이름 변경(rename)해 배치하므로, 빌드가 실패해도 절반만 쓰인 파일이 남지 않으며 이전 빌드의 기존 출력 파일은 새 파일로 대체된다.

### 페이로드 형식

페이로드는 리틀 엔디언(little-endian)으로 기록하며, 문자열은 `u32` 길이와 UTF-8 바이트로 인코딩한다. 페이로드의 최대 크기는 `64 MiB`다. 페이로드 필드의 순서는 다음과 같다.

1. `qxide` 버전
2. 진입점 표시 이름(entry display name)
3. 진입점 소스 텍스트
4. 엔진 이름
5. `shots` (`u64`)
6. `seed` (유무 플래그 + `u64`)
7. `allow-fs` 플래그
8. 프로젝트 정보 (유무 플래그; 패키지 목록의 이름·소스 디렉터리·의존성 인덱스 목록, 진입 패키지 인덱스, 진입 모듈 경로)
9. 파일 목록 (`경로 + 텍스트` 쌍)

트레일러는 파일 끝 32바이트에 리틀 엔디언으로 다음 필드를 순서대로 기록한다.

1. 페이로드 길이 (`u64`, 8바이트)
2. 페이로드의 FNV-1a 64비트 체크섬 (`u64`, 8바이트)
3. 형식 버전 (`u32`, 4바이트 — 현재 `1`)
4. 12바이트 매직 `QXIDE-BUNDLE`

### 실행

`qxide` 바이너리는 시작 시 명령줄 인자를 해석하기 전에 자기 자신의 파일 끝 32바이트를 읽는다. 매직이 일치하지 않으면 일반 `qxide` CLI로 동작한다.

트레일러가 유효하면 내장된 프로그램을 빌드 시 기록된 옵션으로 `qxide run`과 동일하게 실행한다.

- 명령줄 인자는 모두 그대로 `main(String[] args)`에 전달된다(`--` 구분자가 필요 없으며 `--shots` 같은 플래그도 일반 인자로 전달된다).
- `int main()`의 반환값이 프로세스 종료 코드가 된다.
- `std.io`와 `std.env`는 `qxide run`과 동일하게 동작한다.
- 모듈 파일은 페이로드에서만 제공하며, 소스를 찾기 위해 파일 시스템을 조회하지 않는다.
- `std.fs`(빌드 시 `--allow fs`를 지정한 경우에만 허용)는 실행 시점 현재 디렉터리의 `data/`를 사용한다.
- 빌드 시 `--seed`를 지정하지 않았다면 매 실행마다 새 무작위 시드를 사용하며, `qxide run`과 달리 시드 안내 줄을 출력하지 않는다(독립 도구의 `stderr`를 깨끗하게 유지하기 위함이다). 빌드 시 `--seed`와 `--shots`를 지정했다면 출력은 `qxide run --seed S --shots N`과 동일하다.

## 설계 결정

- **번들 우선, AOT 후속**: 언어 프런트엔드(링커, 검사기, 단형화)와 스텝 예산·리소스 제한이 변경 없이 그대로 동작하며 세 엔진(`ast`, `ir`, `jit`)을 모두 사용할 수 있다. 양자 부분(회로와 시뮬레이터)은 어차피 전체 런타임이 필요하다. 고전 코드의 진정한 AOT 컴파일은 Stage 3b에서 다룬다.
- **컴파일된 표현 대신 소스 번들링**: 실행할 때마다 프로그램을 다시 파싱·검사한다. 이로써 진단 동작이 동일하게 유지되고, 별도로 버전을 관리해야 하는 AST/IR 직렬화 형식을 새로 도입하지 않아도 된다. 시작 시 재검사 비용은 아래 `측정` 절에 기록한다.
- **데스크톱 앱 컨테이너 `.qxpak`과의 분리**: `qxide app build`의 `.qxpak` 형식(`docs/design/qx-app.md` 9절)은 별도의 `qxide-app` 런타임이 읽으며 UI 파일을 함께 담는다. 반면 CLI 번들은 `qxide` 바이너리 자체에 덧붙이며 실행 옵션과 체크섬을 함께 보관한다.
- **링커가 읽은 그대로 기록하는 파일 리더**: 빌드 시 파일 리더가 링커가 실제로 읽은 경로와 내용을 그대로 기록하므로, 실행 시점에도 임포트가 빌드 시점과 동일하게 해석된다. 기록되는 경로는 유효한 UTF-8이어야 한다.
- **덮어쓰기 규칙과 오류 종료 코드**: 기존 출력 파일은 덮어쓰되, `.qx` 파일, 디렉터리, 입력 프로그램 자체, 그리고 실행 중인 `qxide` 바이너리는 절대 덮어쓰지 않고 종료 코드 `1`로 실패한다. 사용법 오류(`--backend`, `--engine dual`, 옵션 값 누락 등)는 종료 코드 `2`로 종료한다.
- **프로젝트 의존성 처리**: 프로젝트의 의존성은 `qxide run`과 마찬가지로 먼저 `qxide install`로 설치되어 있어야 하며, 잠금된 패키지 파일 가운데 링커가 실제로 읽은 파일만 번들에 포함된다.

## 무결성과 신뢰

- 트레일러의 체크섬(FNV-1a 64비트)은 잘리거나 손상된 파일을 감지하기 위한 것이며 서명이 아니다. 실행 파일을 수정할 수 있는 사람은 번들된 프로그램과 실행 옵션(권한 포함)도 바꿀 수 있으므로, 번들 실행 파일은 다른 실행 파일과 같은 기준으로 출처를 확인해야 한다. 배포할 때는 플랫폼의 코드 서명을 사용한다.
- 트레일러와 페이로드의 모든 길이와 개수는 읽기 전에 파일 크기와 64 MiB 한도로 검사한다. 손상된 번들은 패닉 없이 종료 코드 1과 다시 빌드하라는 메시지로 끝나고, 매직이 없는 파일은 일반 `qxide`로 동작한다.
- 번들 프로그램은 `qxide run`과 같은 제한 아래에서 실행된다. 스텝 예산과 메모리 한도가 그대로 적용되고, 빌드할 때 허용한 표준 모듈만 쓸 수 있다(`std.fs`는 `--allow fs`로 빌드한 경우에만, 현재 디렉터리의 `data/` 안에서만). 권한은 빌드 시점에 고정되며 실행할 때 인자나 환경 변수로 넓힐 수 없다.
- 실행할 때 모듈 소스는 파일 시스템이 아니라 페이로드에서만 찾으므로, 실행 위치에 있는 다른 `.qx` 파일이 프로그램에 섞여 들어가지 않는다.

## 측정

2026-11-23, Windows 11, release 빌드(`cargo build --release`, `jit` 피처 없음). 같은 PC에서 다른 작업이 함께 실행되던 상태였으며, 시간은 9회 실행의 중앙값이다(같은 측정을 두 번 반복해 두 값을 모두 적었다). 입력은 2,000줄(102,348바이트) 텍스트 파일이다.

| 항목 | 크기 |
| --- | --- |
| `qxide.exe` | 3,919,360바이트 |
| `hello` 번들(`println` 한 줄) | 3,919,474바이트(+114) |
| `examples/cli/wc.qx` 번들 | 3,921,546바이트(+2,186) |

| 명령 | 1회차 | 2회차 |
| --- | --- | --- |
| `qxide --version` | 59.8 ms | 55.9 ms |
| `qxide run hi.qx` | 56.2 ms | 57.4 ms |
| `hi.exe`(번들) | 60.6 ms | 55.8 ms |
| `qxide run wc.qx < words.txt` | 89.4 ms | 87.1 ms |
| `wc.exe < words.txt`(번들) | 80.1 ms | 82.1 ms |
| `qxide run wc.qx -- -f < words.txt` | 85.3 ms | 97.2 ms |
| `wc.exe -f < words.txt`(번들) | 88.1 ms | 94.1 ms |

번들 실행 파일과 `qxide run`의 차이는 측정 잡음(수 ms) 안에 있다. 두 경우 모두 프로그램을 매번 파싱·검사하고 같은 인터프리터로 실행하므로 예상과 일치한다. 작은 프로그램의 시간은 대부분 프로세스 시작 비용이다(`qxide --version`과 비슷함). 이 수치는 번들이 더 빠르다는 근거가 아니며, 번들의 목적은 배포 편의다.

## 한계

- 출력 파일 크기는 `qxide` 바이너리 크기에 소스 크기를 더한 값이다(인터프리터, 시뮬레이터, 모든 `std` 모듈이 항상 포함된다).
- 실행할 때마다 프로그램을 파싱하고 검사한다.
- 크로스 컴파일을 지원하지 않는다(출력 실행 파일은 빌드를 수행한 `qxide`와 같은 플랫폼용이다).
- macOS에서는 바이너리 끝에 데이터를 덧붙이면 코드 서명이 무효화되므로 번들 생성 후 재서명(`codesign --force -s -`)이 필요할 수 있다(아직 테스트하지 않았다).
- 로컬 테스트는 Windows에서만 수행했으며, Linux/macOS CI 검증은 아직 남아 있다.
- QPU 백엔드 옵션(`--backend`)은 번들에서 사용할 수 없다.
- 원본 소스가 바뀌어도 번들은 자동으로 갱신되지 않으므로 다시 빌드해야 한다.

## 다음 단계

- **Stage 3b (`cranelift-object` 기반 AOT)**: 고전 함수를 네이티브 코드로 사전 컴파일하고 양자 런타임 라이브러리와 링크해 독립 네이티브 실행 파일을 생성한다.
- **Stage 3c (JIT 커버리지 확대 및 lowering 캐싱)**: 배열·수학·문자열·구조체로 JIT 대상을 넓히고 lowering 결과를 캐싱한다.
- **경량 런타임 바이너리(선택 과제)**: 개발 도구(LSP, 패키지 매니저 등)를 제외한 별도의 소형 런타임 바이너리를 번들 기반으로 사용해 출력 파일 크기를 줄이는 방안을 검토한다.
