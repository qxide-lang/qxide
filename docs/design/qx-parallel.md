# 병렬 계산 설계 선택지 (Stage 6, 미착수)

## 상태

- 2026-11-24 작성. 구현하지 않았다.
- 로드맵(`docs/design/general-purpose-roadmap.md`) Stage 6(대규모 계산: 공유 데이터 소유권 모델이 있는 데이터 병렬 루프/스레드, SIMD, 고전 GPU 커널)의 완료 기준은 "N-body 시뮬레이션 예제가 멀티 코어에서 실측 속도 향상"이다.
- 언어 문법(새 키워드)과 메모리 모델(공유 값의 표현)은 릴리스 뒤 되돌리기 어려우므로 사용자 결정 전에는 구현하지 않는다.
- 2026-11-24 이후 이 문서의 `Rc`→`Arc` 질문과 공유 값 표현은 메모리 모델 제안(`docs/design/memory-model.md`, 미승인)에 달려 있다. 값 의미론이 채택되면 고유 소유 값은 스레드로 그대로 보낼 수 있어 선택지 A·B의 비용 판단이 달라지며, 동시성은 장기 단계 L1에 해당한다(로드맵 8절).

## 현재 런타임의 제약 (확인한 사실)

- **값 표현**: `String`은 `Rc<str>`, 배열은 `Rc<RefCell<ArrayData>>`(원소 타입별 `Vec<i64>`/`Vec<f64>`/`Vec<bool>`/`Vec<Value>`), 구조체·열거형·`List`/`Map`/`Random`은 `Rc` 참조다(`src/lang/interp.rs` `Value`). `Rc`와 `RefCell`은 스레드 간에 보낼 수 없으므로 현재 값은 다른 스레드로 넘길 수 없다.
- **프로그램·IR·JIT 공유 범위**: 검사된 프로그램(AST)은 `Rc`가 없어 스레드 간 공유가 가능하며, 데스크톱 앱 명령 캐시가 이미 워커 스레드 사이에서 공유한다. IR은 `Rc`를 포함해 공유할 수 없고, JIT 코드도 실행 하나(전개 한 번)에 묶여 있다.
- **스텝 예산**: 모든 엔진이 같은 위치에서 같은 스텝을 과금하고 같은 지점에서 `Q0413`으로 멈춘다(세 엔진 동등성이 테스트의 기준이다). 병렬 실행은 이 결정성을 깨지 않도록 과금 규칙을 정해야 한다.
- **순서 의존 효과**: `std` 효과(`std.io`, `std.fs`, `std.log` 등)와 `println`은 순서가 있는 출력이고, 큐비트 연산은 회로 하나에 순서대로 기록된다. 병렬 영역에서는 이것들을 금지해야 한다.
- **리소스 제한 상향 현황**: 메모리·출력 한도와 `--trusted`(D7, 스텝 `2^36`)는 이미 있으므로 "신뢰 코드의 리소스 제한 상향"은 일부 해결되어 있다.

## 선택지

### A. 순수 함수 병렬 맵 (`std.par` 같은 표준 함수, 복사 전달)

- **내용**: 예로 `double[] r = par.mapDouble(n, step)` 형태로, 부수 효과 없는 함수(검사기가 `std` 호출·출력·큐비트·전역 변경이 없음을 확인)를 인덱스마다 워커 스레드에서 실행하고 결과 배열을 모은다. 입력은 워커마다 복사(깊은 복사)하거나 불변 스냅샷으로 넘긴다. 스텝 과금은 각 인덱스의 스텝을 합산하고, 한도 초과·런타임 오류는 순차 실행이었다면 먼저 일어났을 가장 낮은 인덱스의 오류로 보고하는 규칙이 필요하다.
- **장점**: 새 키워드가 없고, 공유 가변 상태가 없으며, 결과가 순차 실행과 같다.
- **단점/위험**: 함수 값(일급 함수)이 아직 없어 이름으로 함수를 넘기는 문법이 필요하다. 입력 복사 비용이 있다.
- **되돌리기**: 새 키워드나 공유 값 표현(`Rc` 변경) 없이 표준 함수로 시작하므로 상대적으로 되돌리기 쉽다. 다만 함수를 넘기는 문법을 언어에 추가하면 그 문법은 결정 뒤 되돌리기 어렵다.

### B. `parallel for` 루프 (새 문법, 분리된 쓰기)

- **내용**: `parallel for i in 0..n { out[i] = f(i); }`처럼 본문은 바깥 값을 읽기만 하고 미리 선언한 배열의 `i`번 원소에만 쓸 수 있게 검사기가 강제한다.
- **장점**: N-body 시뮬레이션 같은 코드가 자연스럽다.
- **단점/위험**: 새 키워드가 필요하다(`parallel`을 식별자로 쓰는 기존 프로그램이 깨질 수 있어 문맥적 키워드로 해야 한다). 쓰기 분리 검사 규칙이 복잡하다. 배열을 스레드 간에 공유하려면 배열 표현을 `Arc`와 원자적/분할 접근으로 바꿔야 하며, 이는 단일 스레드 성능에도 영향이 있다.
- **되돌리기**: 새 문법과 배열의 공유 표현 변경이 함께 들어가므로 릴리스 뒤 되돌리기 어렵다.

### C. 스레드와 채널 (일반 동시성)

- **내용**: 스레드 생성, 채널, 잠금을 언어에 노출한다.
- **장점**: 가장 일반적이다.
- **단점/위험**: 실행 순서가 비결정적이 되어 세 엔진 동등성·결정적 스텝 과금·재현 가능한 출력이라는 현재 원칙과 충돌한다. 데이터 경합을 막는 소유권 규칙이 필요하다. Stage 6 목표(데이터 병렬)보다 범위가 크다.
- **되돌리기**: 언어 문법, 소유권 규칙, 런타임 메모리 모델을 전반적으로 바꾸게 되어 릴리스 뒤 되돌리기 어렵다.

### D. SIMD와 고전 GPU 커널

- **내용**: Cranelift의 벡터 타입이나 GPU 백엔드(저장소의 `gpu` 피처는 상태 벡터 시뮬레이터용 CubeCL 프로토타입)로 고전 루프를 실행한다.
- **장점**: A나 B가 정한 병렬 영역 규칙 위에서 고전 루프를 벡터·GPU 백엔드로 실행하는 경로를 연다.
- **단점/위험**: A나 B가 정한 병렬 영역 규칙이 선행되지 않으면 의미가 없다. 현재 저장소의 `gpu` 피처는 상태 벡터 시뮬레이터용 CubeCL 프로토타입이다.
- **되돌리기**: A나 B의 병렬 영역 규칙이 확정된 뒤에 그 위의 실행 경로로 다루므로, 선행 선택지가 정해진 뒤 별도로 판단한다.

## 권장안

- **A를 먼저**: 표준 함수 하나(예: 정수·실수 결과 배열을 만드는 병렬 맵)로 시작하면 새 키워드 없이 되돌리기 쉽고, 결정성 규칙(스텝 합산, 가장 낮은 인덱스의 오류 보고)을 먼저 검증할 수 있다. 함수를 넘기는 방법(함수 이름 문자열 대신 함수 참조 문법)이 먼저 정해져야 한다.
- **실행 환경별 워커 수**: 워커 수 기본값은 사용 가능한 코어 수이되 명령줄 옵션으로 줄일 수 있게 한다. 플레이그라운드(wasm)·REPL·데스크톱 앱에서는 순차 실행으로 같은 결과를 낸다.
- **후속 범위**: B는 A의 실측 결과(복사 비용이 병목인지)를 본 뒤 검토하고, C는 Stage 6 범위에서 제외한다. D는 A나 B의 병렬 영역 규칙이 정해진 뒤에 다룬다.

## 사용자가 정해야 할 것

- **방향 선택**: A(표준 함수) / B(새 문법) / C 중 방향.
- **함수 참조 문법**: 도입 여부와 형태(A에 필요).
- **결정성 규칙**: 병렬 영역의 스텝 과금(각 인덱스 스텝 합산)과 오류 보고 규칙(순차 실행이었다면 먼저 일어났을 가장 낮은 인덱스의 오류 보고)으로 위 권장 규칙을 채택할지.
- **공유 값 표현 변경 허용 여부**: `Rc` → `Arc` 변경을 허용할지. 단일 스레드 성능과 wasm 크기에 영향이 있을 수 있다(측정하지 않았다).

## 측정하지 않은 것

- 이 문서의 비용·성능 관련 서술은 추정이며 측정하지 않았다.
- 멀티 코어 벤치마크는 실행하지 않았다(이 세션은 다른 세션의 측정 때문에 CPU 병렬도를 절반 이하로 제한했다).

## 동시성: 스레드와 비동기 (2026-11-24 추가, 미구현)

장기 계획 1단계(로드맵 8.4절 L1)의 동시성 항목이다. 위 선택지 A~D는 데이터 병렬을 다뤘고, 이 절은 일반 스레드와 비동기를 메모리 모델 제안(`docs/design/memory-model.md`)에 맞춰 정리한다. 구현하지 않았다. 이유는 끝에 적었다.

### 메모리 모델과의 관계

- 값 의미론에서는 큰 값이 한 이름만 가진다(이동하거나 `.copy()`). 그래서 값을 `consume`으로 다른 스레드에 넘기면 원래 스레드에는 그 값이 남지 않아 데이터 경합이 생기지 않는다(메모리 모델 7절 H5). 이것이 C(스레드와 채널)의 가장 큰 위험이던 "데이터 경합을 막는 소유권 규칙"을 대신한다.
- 남는 공유는 `Shared<T>`다. 스레드 사이에서 쓰려면 잠금이 있는 별도 타입(가칭 `Mutex<T>`)이 필요하고, `Shared<T>`는 한 스레드 안에서만 쓰게 해야 한다.
- 지금 런타임 값은 `Rc`라서 다른 스레드로 보낼 수 없다. 값 의미론이 런타임 표현까지 바뀌어야(M5) 고유 소유 값을 `Rc` 없이 표현할 수 있고, 그때 스레드로 보내는 비용이 정해진다. 따라서 스레드 구현은 M5 뒤에 와야 한다.

### 안 (임시, 사용자 확인 필요)

- **스레드**: `Task<T> t = spawn(work, consume input);`처럼 함수와 `consume` 인자로 새 작업을 만들고 `T r = t.join();`으로 결과를 받는다. 함수를 값으로 넘기는 문법이 필요하다(위 A와 같은 선행 조건).
- **채널**: `Channel<T>`의 `send(consume T v)`와 `receive()`. 보낸 값은 이동하므로 보낸 쪽에서 다시 쓸 수 없다(`Q0321`과 같은 규칙).
- **결정성**: 스레드 실행은 순서가 비결정적이다. 스텝 예산은 스레드마다 따로 세고, 세 엔진 동등성 테스트는 스레드를 쓰지 않는 프로그램과 결정적인 패턴(`spawn` 뒤 바로 `join`)으로 한정한다. 출력(`println`)은 줄 단위로 섞일 수 있다고 문서에 밝힌다.
- **비동기**: 데스크톱 앱 명령과 입출력(`std.fs`, 앞으로의 네트워크)을 위한 것이다. 언어에 `async`/`await`를 넣기보다 먼저 스레드와 채널로 표현하고, 앱 런타임이 이미 쓰는 워커 스레드에서 실행하는 쪽이 되돌리기 쉽다. `async` 문법은 표준 라이브러리 수요를 본 뒤에 정한다.
- **실행 환경**: 플레이그라운드(wasm)와 REPL에서는 `spawn`을 순차 실행으로 대신해 같은 결과를 낸다.

### 되돌리기 어려운 것

- 함수를 값으로 넘기는 문법, `spawn`/`Channel`/`Mutex`의 이름과 규칙, 런타임 값의 스레드 간 표현(`Rc`에서 `Arc` 또는 고유 소유).

### 이번에 구현하지 않은 이유

- 스레드로 값을 보내려면 런타임 표현이 바뀌어야 하고(M5), 그 전에 구현하면 모든 값을 `Arc`로 바꿔야 해서 단일 스레드 성능과 wasm 크기에 영향이 있다(측정하지 않음). 메모리 모델 자체가 아직 승인 전이다.
- 함수를 값으로 넘기는 문법이 아직 없다.
- 그래서 순서는 메모리 모델 승인, M5, 함수 참조 문법, 위 A(병렬 맵), 그다음 스레드·채널로 권한다.
