# `qxide` GPU 백엔드 (`gpu` 피처)

## 개요 및 사용법

`qxide`의 GPU 시뮬레이션 백엔드는 기본 비활성화 상태이며, Cargo 피처 `gpu`로 활성화합니다.

- 테스트 실행: `cargo test --features gpu`
- 벤치마크 실행: `cargo run --release --features gpu --example gpu_bench [max_qubits]`

공개 API에서는 `c.simulate_with(Backend::Gpu, seed)` 형태로 사용합니다. `Backend` 열거형은 `#[non_exhaustive]`이며, `Backend::Gpu` 배리언트는 `gpu` 피처가 활성화된 경우에만 존재합니다.

GPU 런타임 의존성으로는 CubeCL 0.11.4(`cubecl` 크레이트, 기본 피처 비활성화, `wgpu` 피처 활성화)를 사용합니다. CubeCL은 공식 README 기준으로 현재 알파(alpha) 단계입니다.

## 설계 (프로토타입)

- **정밀도 및 버퍼 구조**: GPU 상의 상태 진폭은 실수부/허수부 분리 버퍼를 사용하는 `f32`로 표현합니다. CubeCL에서 WGSL/`wgpu`의 `f64` 지원은 어댑터가 `SHADER_F64`(또는 Vulkan `shader_float64`)를 노출할 때만 조건부로 등록되기 때문입니다.
- **커널과 2D 디스패치**: 커널은 세 가지로, 범용 2x2 단일 큐비트 게이트 커널, `cx` 커널, `ccx` 커널로 구성됩니다. 스레드는 단일 게이트의 경우 진폭 쌍당 1개, `cx`의 경우 진폭 4개 묶음(quadruple)당 1개, `ccx`의 경우 진폭 8개 묶음당 1개를 할당합니다. `wgpu`가 디스패치 차원당 워크그룹 수를 65535개로 제한하므로 2D 그리드 디스패치를 사용합니다.
- **유니타리 프리픽스(prefix) 실행 및 CPU 폴백**: 회로의 유니타리 프리픽스(첫 번째 `measure`/`reset`/`branch` 이전까지의 단일 큐비트 게이트, `cx` 및 `ccx`)만 GPU에서 실행합니다. 이후 상태 벡터를 CPU의 `f64` 상태 벡터로 읽어 들인 뒤, 동일한 시드와 난수 스트림을 사용해 CPU 백엔드가 나머지 실행을 마무리합니다. 따라서 초반에 측정이 있는 회로는 이점이 적고, 마지막에만 측정이 있는 회로는 거의 전체가 GPU에서 실행됩니다.
- **메모리 제한**: GPU 백엔드에도 메모리 제한(`Circuit::set_memory_limit`, 기본값 1 GiB)이 동일하게 적용됩니다. GPU 자체는 `2^n × 8`바이트가 필요하지만, CPU로의 `f64` readback에 `2^n × 16`바이트가 필요하기 때문입니다.
- **백엔드 경계**: 향후 다른 GPU 백엔드(예: CUDA 기반)를 추가할 때를 대비한 경계 함수는 `gpu::run_prefix(ops, n_qubits) -> (state, ops_consumed)`입니다. 이 함수는 GPU에서 실행된 프리픽스 이후의 상태와 소비된 연산 수를 반환하며, 새 GPU 런타임은 이 동일한 함수만 구현하면 됩니다.

## 정확도

- **무작위 회로 비교**: 1~12큐비트 범위에서 `h`, `s`, `t`, `x`, `rx`, `ry`, `rz`, `cx`, `ccx`(무작위 각도, 3큐비트 이상에서 `ccx` 포함)로 구성된 최대 200개 게이트의 무작위 회로 40개를 대상으로 `f64` CPU 백엔드와 비교했으며, 진폭당 절대 오차 `< 1e-4`를 만족합니다.
- **`ccx` 진리표 검증**: 6가지 역할 순서(role order) × 8가지 기저 입력 전체에 대해 GPU에서 `ccx` 진리표를 CPU와 비교 검증합니다.
- **26큐비트 대규모 검증**: 모든 큐비트에 `H`를 적용한 뒤 `z`, 이어서 최상위 큐비트가 제어하는 `cx`를 실행하는 26큐비트 테스트에서 `2^26`개 진폭 전체를 `1e-7` 오차 이내로 검증했습니다. 이 테스트는 워크그룹 65535개를 초과하는 2D 디스패치 동작도 함께 검증합니다.
- **공개 API 테스트**:
  - `H T^4 H` 회로가 GPU에서 결정론적으로 동작함을 확인합니다.
  - 분기(`branch`)를 포함한 텔레포테이션 회로에서 동일 시드 기준 CPU와 동일한 결과를 내는지 검증합니다(`f32` 반올림으로 인해 임계값에 정확히 걸친 샘플이 뒤집힐 수 있어 300샷당 최대 2비트의 차이는 허용).
  - 메모리 제한이 정상적으로 강제되는지 확인합니다.

## 성능 측정

### 측정 환경

- OS: Windows 11
- CPU: Intel Core i9-14900HX (CPU 백엔드는 단일 스레드 `f64`)
- GPU: NVIDIA GeForce RTX 4070 Laptop GPU 8 GB (드라이버 581.57)
- 런타임/툴체인: CubeCL 0.11.4 `wgpu` 런타임(어댑터 보고명 `wgpu<wgsl>`), Rust 1.99.1, release 빌드

### 측정 방법

- **벤치마크 회로**: (모든 큐비트에 `h`, 모든 큐비트에 `rz`, 인접 큐비트 간 `cx` 체인) 2개 레이어로 구성됩니다.
  - `gates` 모드: 측정 없음
  - `measured` 모드: 마지막에 모든 큐비트를 측정
- **측정 기준**: 워밍업 실행으로 디바이스 초기화 및 커널 컴파일 시간을 제외한 뒤, GPU 업로드와 readback을 포함한 `simulate_with` 전체(end-to-end) 실행 시간의 중앙값을 사용했습니다(20큐비트 이하 5회 실행, 그 이상 3회 실행).

### 관찰

- 약 16큐비트 미만에서는 고정 커널 실행/전송 오버헤드(약 2 ms) 때문에 GPU가 CPU보다 느립니다.
- `gates` 모드에서는 24~26큐비트에서 약 11배의 가속을 보입니다.
- `measured` 모드에서는 가속 배율이 약 3.5~4배 수준에 머무릅니다. 두 백엔드 모두 모든 `n`개 큐비트를 CPU에서 측정하는 데 `O(n * 2^n)` 비용이 들며 이 구간이 전체 시간을 지배하기 때문입니다.
- 비교 대상인 CPU 백엔드는 단일 스레드이므로, 멀티스레드 CPU 백엔드와 비교하면 격차가 줄어듭니다.
- 28큐비트 이상은 측정하지 않았습니다(`f64` readback에만 4 GiB가 필요하며, 테스트 머신의 가용 메모리가 약 8 GiB 수준이었기 때문입니다).

## 한계와 다음 단계

- **GPU 내 측정 및 리셋**: 상태 벡터를 CPU로 readback하지 않도록 GPU에서 확률 리덕션(probability reduction) 커널을 통해 측정과 리셋을 직접 처리합니다.
- **게이트 퓨전(gate fusion)**: 연속된 게이트를 결합해 커널 호출과 메모리 왕복을 줄입니다.
- **멀티스레드 CPU 기준선**: 공정한 성능 비교를 위해 멀티스레드 CPU 백엔드 기준선을 마련합니다.

## `cuda-oxide` 조사 (향후 검토 사항, 미구현)

- **개요**: `cuda-oxide`는 NVIDIA의 공식 프로젝트입니다. 기존 저장소(`https://github.com/NVlabs/cuda-oxide`)는 `https://github.com/NVIDIA/cuda-rust`("NVIDIA's CUDA platform for Rust")로 리다이렉트되며, `cuda-oxide`는 타일 모델인 `cutile-rs`와 나란히 위치하는 SIMT 컴포넌트이자 커스텀 `rustc` 코드젠 백엔드입니다. 문서는 `https://nvidia.github.io/cuda-rust/`에 있습니다. (커뮤니티 프로젝트인 Rust-CUDA / Rust-GPU와는 별개입니다.)
- **상태 및 라이선스**: 프로젝트 스스로 "초기 단계의 연구 프로젝트이며 버그, 미완성 기능, API 변경이 예상됨(an early-stage research project. Expect bugs, incomplete features, and API breakage.)"으로 명시하고 있습니다. 최신 릴리스는 `cuda-oxide` v0.4.0(2026-11-11)이며 라이선스는 Apache-2.0입니다.
- **툴체인**: 초기 릴리스(v0.1.0)는 nightly Rust를 고정했으나, 현재는 stable Rust 1.99.1과 `rustc-dev`, `llvm-tools` 컴포넌트를 고정 사용합니다.
- **지원 플랫폼 및 요구사항**:
  - Linux(Ubuntu 24.04 테스트) 및 Windows(`x86_64-pc-windows-msvc`, Windows 10 22H2 / Windows 11 지원이 공식 북에 문서화됨).
  - CUDA 13.0+, LLVM/Clang 21+, Ampere 이상 GPU(`sm_80`+), 드라이버 580+가 필요하며, Windows에서는 Visual Studio 2022 및 `vcpkg` `libffi`도 요구됩니다.
- **`qxide`에 대한 결론**: 초기 계획에서는 `cuda-oxide`가 Linux 및 nightly 전용일 것으로 가정했으나 현재는 그렇지 않습니다. 다만 여전히 API 변경이 잦고 툴체인 요구사항이 무거운 초기 연구 소프트웨어이므로, `qxide`는 첫 번째 GPU 백엔드로 CubeCL을 유지하고 향후 앞서 정의한 `run_prefix` 경계 뒤에서 `cuda-oxide` 도입을 재검토합니다. 개발 PC(RTX 4070 Laptop은 Ada 아키텍처 `sm_89`, 드라이버 581.57, CUDA 13.0 툴킷 설치됨)는 명시된 하드웨어 및 CUDA 요구사항을 충족합니다.
